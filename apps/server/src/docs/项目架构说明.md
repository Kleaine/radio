# AI 音乐电台 — 分工5 架构说明

> 阅读对象：全组成员，特别是分工2（后端）和分工1（前端）
> 阅读时间：15 分钟

---

## 一、为什么是这种骨架

打开我们的交付物，你会看到这样的结构：

```
交付物/
├── apps/server/
│   ├── .env.example                  ← 环境变量模板
│   └── src/
│       ├── services/                 ← 业务逻辑（分工5 核心产出）
│       ├── prompts/                  ← AI 提示词
│       ├── docs/                     ← 文档
│       └── interface/                ← 跨模块接口
├── data/
│   └── schedule.txt                  ← 日程数据
└── user/
    ├── taste.md                      ← 音乐品味
    ├── routines.md                   ← 作息习惯
    └── mood-rules.md                 ← 情绪规则
```

> `package.json`、`tsconfig.json` 等工程配置文件由分工2 搭建项目骨架时创建，不属于分工5 交付范围。

这不是随便建的。下面逐层解释为什么。

---

### 1.1 为什么有 `apps/`

这个项目是一个 **monorepo**（单仓多包）结构。整个系统有两个独立的应用：

| 应用 | 路径 | 职责 |
|---|---|---|
| 前端 | `apps/web/` | React 播放器页面（分工1） |
| 后端 | `apps/server/` | API 服务 + AI + 外部接口（分工2 + 分工5） |

`apps/` 把它们装在一起，共享一份 `node_modules`，一个 `pnpm install` 安装所有依赖。

分工作5 交付的是 `apps/server/src/` 下的内容。

---

### 1.2 为什么有 `services/`

后端代码按职责分了四个目录：

```
apps/server/src/
├── services/    ← 业务逻辑（最重要的目录）
├── routes/      ← HTTP 路由（分工2 负责）
├── prompts/     ← AI 提示词文件
├── docs/        ← 文档
└── interface/   ← 跨模块接口定义
```

`services/` 是"干活的地方"——每个文件封装一个外部系统或一项独立能力。

**为什么不用一个文件写完？** 因为每个 service 有独立的 Mock 实现。Mock 模式下不依赖任何外部 API，全流程能跑。真实模式下才去调外部接口。如果全写一个文件里，Mock 和真实的切换逻辑会搅成一团。

---

### 1.3 为什么每个 Service 都分 Mock 和真实

这是 **Mock-First 开发模式**：

```
启动时判断：
  有 API Key？ → 用真实实现（调豆包、调QQ音乐、调OpenWeather）
  没有 Key？  → 用 Mock 实现（返回假数据，但格式一样）
```

好处：
- 没有 API Key 也能启动看到完整 UI
- 答辩时某个 API 挂了，Mock 兜底不翻车
- 换音乐平台（比如 QQ 音乐换网易云）只换实现，接口不变

---

## 二、逐文件说明

### 2.1 `.env` — 环境变量（敏感信息）

**一句话**：存 API Key 的地方。**这个文件不能提交到 git。**

代码里调外部 API 需要 Key。如果写在 `.ts` 文件里，一上传 GitHub 全世界都能用你的额度。`.env` 避免这个问题——代码只读环境变量，变量值存在 `.env` 文件里，`.gitignore` 保证它不会被提交。

```env
DOUBAO_API_KEY=ark-xxxxx          ← 豆包 API Key（分工5 已填）
QQ_MUSIC_COOKIE=uin=xxx; qm...    ← QQ 音乐 Cookie（分工5 已填）
OPENWEATHER_API_KEY=xxx           ← 天气 Key（分工5 已填）
CITY=Beijing
```

**分工5 已全部填好**，分工2 不需要额外申请任何 Key。

---

### 2.2 `data/schedule.txt` — 日程数据

**一句话**：纯文本，一行一条日程。人可以直接改，机器也能读。

格式宽容，三种写法都行：
```
09:00-10:30 软件工程课
14:00 实验室
交作业
```

`calendar.service.ts` 负责读写这个文件。用户也可以在聊天框里说"明天上午答辩"，AI 自动更新它。

---

### 2.3 `user/taste.md`、`routines.md`、`mood-rules.md` — 用户画像

**一句话**：三个 Markdown 文件，记录 AI 在对话中发现的用户偏好。

| 文件 | 记什么 | 谁写 |
|---|---|---|
| `taste.md` | 音乐品味（喜欢什么风格、歌手） | `memory-writer.ts` 自动追加 |
| `routines.md` | 作息习惯（什么时间听什么） | `memory-writer.ts` 自动追加 |
| `mood-rules.md` | 情绪规则（什么心情配什么歌） | `memory-writer.ts` 自动追加 |

初始是空的，用得越久内容越多，AI 推荐越准。

**为什么用 .md 而不是数据库**：三个文件加起来几 KB。人类直接打开就能看懂，机器也能解析。课设没必要上数据库。

---

### 2.4 `services/llm.service.ts` — AI 大脑（核心文件）

**一句话**：跟豆包大模型对话，把回复解析成结构化数据。

**做了什么**：
1. 读 `plan-system.md`（AI DJ 小雨的人设卡）作为 System Prompt
2. 把用户说的话 + 上下文拼成一条消息
3. 调豆包 API，开启流式输出（字一个字蹦给前端）
4. 从豆包的回复里提取 JSON（三层容错：直接解析 → 提取代码块 → 正则匹配）
5. 解析成功返回 `PlanResponse`（`{ summary, scene, items[], memory?, schedule? }`）
6. 解析失败返回默认播报计划（DJ 开场白 + 两首歌 + 串词）

**输入**：用户说的话 + 上下文文本
**输出**：`PlanResponse` 对象，包含 summary、scene、items（song/tts 交替序列）、schedule、memory

**被谁调用**：分工2 在 `/api/dispatch` 路由中调用

**依赖**：`openai` npm 包、`plan-system.md`、`memory-writer.ts`

---

### 2.5 `services/context.service.ts` — 上下文组装

**一句话**：把 AI 需要知道的"背景信息"拼成一段文本。

**做了什么**：
1. 获取当前时间（北京时间）
2. 调天气服务拿温度和天气描述
3. 调日历服务拿今天的日程
4. 读最近播放记录（由分工2 的 DB 提供）
5. 读用户画像文件（taste.md、routines.md、mood-rules.md）
6. 全部拼成一段文字

**为什么 AI 需要这些**：如果只问 AI"推荐几首歌"，它乱推。如果告诉它"现在是晚上10点，下雨，你最近在听陈绮贞"，它自然会推安静治愈的歌。

**拼出来的文本长这样**：
```
当前时间：2026/5/31 22:00:00
天气：Beijing 22°C 小雨
今日日程：14:00-16:00 实验室
最近播放：旅行的意义、Summer、Don't Know Why
用户音乐偏好：喜欢轻音乐、爵士、治愈系钢琴
用户说：好累，来点放松的
```

**被谁调用**：分工2 在 `/api/dispatch` 中，调 LLM 之前调用

---

### 2.6 `services/music.service.ts` — QQ 音乐

**一句话**：搜歌、拿播放链接、拿歌词。带 Mock 兜底。

**两个实现**：

| 实现 | 什么时候用 | 干什么 |
|---|---|---|
| `MockMusicService` | 没有 Cookie 或 npm 包没装 | 返回假歌名假歌手（周杰伦、林俊杰、陈奕迅……） |
| `QQMusicService` | 有 Cookie 且 npm 包已装 | 调 `qq-music-api` 真实搜索 |

**接口**（由 `interface/music.service.interface.ts` 定义）：
- `search(keyword)` → 返回歌曲列表（id、歌名、歌手、专辑、封面、时长）
- `getSongUrl(songId)` → 返回可播放的音频 URL
- `getLyric(songId)` → 返回 LRC 歌词

**为什么分开定义接口和实现**：分工作5 定义接口（约定输入输出），分工2 对着实现。如果 npm 包不好用要换，分工2 只改 `QQMusicService` 内部代码，接口不变，调用方不受影响。

---

### 2.7 `services/weather.service.ts` — 天气

**一句话**：拿天气数据，三层回退。

```
尝试 OpenWeatherMap（需 API Key）
    ↓ 失败了？
尝试 Wttr.in（免费，无需注册，无需 Key）
    ↓ 也失败了？
返回 Mock（"晴，22°C"），或用上次成功的缓存
```

**输出**：`{ temp: 22, description: "小雨", city: "Beijing" }`

**为什么三层**：代码量增加 30 行，但天气永远不会成为系统的崩盘点。答辩时网络不好也不怕。

---

### 2.8 `services/calendar.service.ts` — 日程

**一句话**：读 `data/schedule.txt`，也支持从 AI 聊天中更新。

**两种入口**：

| 入口 | 怎么用 |
|---|---|
| 手动编辑 | 打开 `data/schedule.txt`，一行一条日程 |
| AI 聊天 | 用户说"明天上午十点答辩"，AI 返回 `schedule` 字段，自动写回 txt |

**schedule.txt 格式**（宽容，三种写法都行）：
```
09:00-10:30 软件工程课
14:00 实验室
交作业
```

**后期升级**：如果想在网页里改日程，分工1 加一个文本框，后端调 `calendarService.updateEvents()` 就行。代码不用动。

---

### 2.9 `services/memory-writer.ts` — 偏好记忆

**一句话**：AI 发现用户新偏好后，自动记到本地文件。

**流程**：
```
AI 回复 JSON 里带 memory 字段
  → [{ "file": "taste", "add": "用户喜欢治愈系钢琴" }]
    → 追加一行到 user/taste.md
      → 下次对话时，context.service 读到这条
        → AI 知道"用户喜欢治愈系钢琴"
```

**为什么不是数据库**：课设规模下，三个 markdown 文件够了。人类可以直接打开看，机器也能读。

---

### 2.10 `prompts/plan-system.md` — AI DJ 人设卡

**一句话**：告诉豆包"你是谁、怎么说话、输出什么格式"。

这个文件决定了整个系统的"灵魂"——AI DJ 小雨的性格、说话方式、推荐风格、边界规则，全在这里定义。

**为什么单独一个文件而不是写死在代码里**：改 prompt 像改文档一样简单，不需要改代码。试了效果不好，直接编辑这个文件就行。

---

### 2.11 `interface/music.service.interface.ts` — 接口定义

**一句话**：约定音乐服务的输入输出格式。

分工作5 定义，分工2 实现。相当于两个人之间的合同——只要接口不变，两边各写各的，不会互相阻塞。

---

### 2.12 `docs/意图规则表.md` — 正则分流规则

**一句话**：用户说的话，先正则匹配，匹配不到才调 AI。

三层漏斗节省 AI 调用次数（AI 调用又慢又花钱）：
- 第1层："下一首"、"暂停" → 直接执行
- 第2层："播放周杰伦" → 直接搜歌
- 第3层："好累想听点轻松的" → 调 AI

---

### 2.13 `docs/API协同流程.md` — 数据流图

**一句话**：从用户输入到歌曲播放的完整链路，标注了每个环节谁负责。

## 三、文件依赖关系

```
分工2 的 /api/dispatch 路由
    │
    ├── context.service.ts
    │   ├── weather.service.ts
    │   ├── calendar.service.ts
    │   └── memory-writer.ts（读 user/）
    │
    ├── llm.service.ts
    │   ├── prompts/plan-system.md
    │   └── memory-writer.ts（写 user/）
    │
    └── music.service.ts
        └── interface/music.service.interface.ts
```

箭头方向是"谁调谁"。分工2 只需要调 `/api/dispatch` 里暴露的几个函数，不需要知道内部细节。

## 四、分工5 和分工2 的边界

分工5 交付的是 service 层的**代码**，分工2 在路由层**使用**它们。所有 service 都通过工厂函数创建，分工2 只需传入配置即可。

| 文件 | 如何创建 | 分工2 在哪调用 |
|---|---|---|
| `llm.service.ts` | `createLlmService({ apiKey })` | 流式：`llmService.generatePlanStream()` / 后台：`llmService.generatePlan()` |
| `context.service.ts` | `createContextService({ weatherService, calendarService, memoryWriter })` | 调 LLM 前 `contextService.build()` |
| `music.service.ts` | `new QQMusicService(cookie)` 或 `new MockMusicService()` | 搜索阶段和 enrich 阶段调 `search()` |
| `weather.service.ts` | `createWeatherService({ openWeatherApiKey, city })` | 传入 `createContextService()` |
| `calendar.service.ts` | `createCalendarService(dataDir)` | 传入 `createContextService()` |
| `memory-writer.ts` | `createMemoryWriter(userDir)` | 传入 `createContextService()`；LLM 返回后调 `writeAll()` |
| `music.service.interface.ts` | 接口定义 | `QQMusicService` 和 `MockMusicService` 均已实现，直接用 |

分工5 不写路由、不写数据库、不写前端。所有文件都是 service 层，被分工2 的路由层调用。
